# Nakna P9.31 — แก้ทางตันเพิ่มพนักงานเมื่อ Trial หมด

## สาเหตุและขอบเขต
ภาพแจ้งเตือนตรงกับเงื่อนไข `assertSeatCapacity()` ของ P9.30: ทั้งการเพิ่มผ่าน HR, รับพนักงานจาก Recruitment และสมัครผ่านลิงก์เรียกตัวตรวจเดียวกัน บริษัทที่ Trial หมดจะถูกบล็อกก่อน INSERT พนักงาน

ตรวจได้จากไฟล์ต้นทางและทดสอบด้วยข้อมูลจำลอง ไม่ได้ตรวจวันหมดอายุหรือสถานะชำระเงินจริงของบริษัทใน D1 ที่ใช้งานอยู่ จึงไม่ถือว่าบริษัทจ่ายเงินแล้วหรือได้รับสิทธิ์ใช้ฟรีโดยอัตโนมัติ

**ติดตั้งแพตช์อย่างเดียวไม่ต่อ Trial อัตโนมัติ** ผู้ดูแลระบบนากนะต้องเลือกบริษัทและยืนยันวันสิ้นสุด/เหตุผลก่อน บริษัทอื่นยังใช้เงื่อนไขเดิม

## ฟีเจอร์แก้ไข
- ผู้ดูแลระบบนากนะกด “ต่อทดลองใช้บริษัทนี้” ได้ในหน้าแพ็กเกจ หรือกด “ต่อทดลองใช้” ข้างบริษัทใน Nakna Admin
- เลือกวันสิ้นสุดแน่นอน (หลังวันนี้ ไม่เกิน 30 วันจากวันนี้) และกรอกเหตุผล 5–500 ตัวอักษร
- ยังคงวันเริ่มทดลองเดิม ต่อเฉพาะวันสิ้นสุดที่เลือก ไม่เลื่อนวันหมดอายุทุกครั้งที่เข้าเว็บ
- ไม่เปลี่ยนแพ็กเกจเป็นชำระเงิน ไม่สร้าง Invoice หรือ Payment และไม่เพิ่มจำนวน Seat
- บริษัทที่ถูกยกเลิก, แพ็กเกจที่ไม่ใช่ Trial, หรือบริษัทที่มีรายการบิล/การชำระเงิน ต้องตรวจสถานะในงาน Billing เดิม ไม่ให้ปุ่มต่อ Trial ข้ามเงื่อนไขเหล่านี้
- บันทึกผู้ดำเนินการ บริษัท เหตุผล วันหมดอายุเก่า/ใหม่ใน audit_logs พร้อมการอัปเดตแบบ transaction
- หน้าสมัครตรวจสิทธิ์ตั้งแต่เปิดลิงก์ ไม่ให้พนักงานเข้าใจว่าต้องซื้อแพ็กเกจเอง
- มี “ตรวจสิทธิ์อีกครั้ง” โดยไม่ล้างข้อมูลที่กรอกในหน้าเดิม ข้อมูลยังอยู่เฉพาะตอนเปิดหน้านั้น ไม่บันทึกแบบฟอร์มส่วนบุคคลเพิ่มลง localStorage/sessionStorage
- POST ตรวจซ้ำเสมอ แม้แก้ JavaScript หรือข้ามหน้าตรวจสิทธิ์ก็ข้าม Seat/Trial ไม่ได้
- ข้อผิดพลาดเพิ่มพนักงานแยก Trial หมด, Subscription หมด, ยกเลิก, Seat เต็ม และการตั้งค่าผิดออกจากกัน
- ปุ่มเปลี่ยน Trial status เดิมจะไม่แสร้งว่าสำเร็จหากวันสิ้นสุดเก่าหมดแล้ว แต่บอกให้ใช้ปุ่มต่อทดลองใช้
- ลิงก์เชิญที่ยังไม่หมดอายุและยังไม่ถูกใช้ครบกลับมาใช้ได้หลังจัดการสิทธิ์; ลิงก์ที่หมดอายุแล้วต้องขอใหม่ ไม่ปลดล็อกโทเคนเก่า

## ติดตั้ง
ใช้ต่อจาก P9.30 และไฟล์หน้าบ้านจากแพตช์ก่อนหน้า บันทึกสำรองเฉพาะไฟล์ที่จะทับก่อน

วางทับทั้งหมด 7 ไฟล์ตามโฟลเดอร์:

```
src/index.js
public/app.js
public/index.html
public/styles.css
public/invite.js
public/invite.html
public/invite.css
```

อย่านำ `src/index.js` ไปวางที่ root และอย่าสร้างโฟลเดอร์ release ซ้อนเข้าไปในโปรเจกต์

```
npm run check
npx wrangler deploy
```

ไม่มี Migration ใหม่ ไม่ต้องเปลี่ยน wrangler.jsonc หรือ DB binding

## เปิดให้ทีมสมัครได้ (ต้องทำหลังติดตั้ง)
1. เข้า Dashboard ด้วยบัญชีของผู้ดูแลระบบนากนะ (SaaS Admin)
2. ไปที่ ตั้งค่า > แพ็กเกจ/Subscription ของบริษัทที่ต้องการ หรือเมนู Nakna Admin > Workspace ทั้งหมด
3. ตรวจชื่อบริษัท แล้วกด “ต่อทดลองใช้บริษัทนี้” / “ต่อทดลองใช้”
4. เลือกวันสิ้นสุดใหม่ กรอกเหตุผล แล้วกด “ยืนยันต่อทดลองใช้”
5. ตรวจว่าสถานะกลับเป็นทดลองใช้ และยังมีจำนวน Seat เพียงพอ
6. ให้พนักงานกด “ตรวจสิทธิ์อีกครั้ง” ในหน้าใหม่ของ P9.31 แล้วส่งแบบฟอร์มเดิม หรือให้ HR ลองเพิ่มใหม่

หากกำลังเปิดฟอร์มเวอร์ชันเก่าค้างอยู่ ปุ่มใหม่จะยังไม่ปรากฏ ต้องเปิดหน้าใหม่หลัง Deploy และอาจต้องกรอกใหม่ครั้งนั้น ระบบไม่สามารถกู้แบบฟอร์มที่ปิดไปแล้วก่อนติดตั้งแพตช์นี้ได้

## กรณีไม่มีเมนู Nakna Admin
บทบาท Owner / Co-Owner / HR ของบริษัท ไม่ได้เท่ากับผู้ดูแลระบบนากนะทุกบริษัท

ใช้ allowlist ที่ระบบมีอยู่แล้วชื่อ `NAKNA_ADMIN_EMAILS` เป็นอีเมลที่บัญชีผู้ดูแลใช้ล็อกอิน Dashboard จริง ไม่ใช่อีเมลของพนักงานที่กำลังสมัคร

ตัวเลือก Cloudflare Dashboard:
Workers & Pages > hr-line > Settings > Variables and Secrets > Add > Secret
Name: NAKNA_ADMIN_EMAILS
Value: อีเมลล็อกอินของผู้ดูแลที่ได้รับอนุญาต (หลายอีเมลคั่นด้วย comma)
จากนั้นบันทึกและ Deploy แล้วรีเฟรช Dashboard

หรือรัน:
```
npx wrangler secret put NAKNA_ADMIN_EMAILS
```
แล้วกรอกค่าเมื่อ CLI ถาม **ไม่ต้องใส่อีเมล/secret ลงใน source code หรือส่งรหัสผ่านมาในแชต** ถ้ามีค่าเดิมอยู่ ให้เก็บอีเมลผู้ดูแลเดิมไว้ ไม่เขียนทับทิ้งโดยไม่ตรวจสอบ

การเพิ่มอีเมลในรายการนี้ให้สิทธิ์ Nakna SaaS Admin ทุกบริษัทตามระบบเดิม จึงให้เฉพาะผู้ดูแลแพลตฟอร์มที่เชื่อถือได้ ไม่ให้ HR ของบริษัทลูกค้า

หากบริษัทมีแพ็กเกจชำระเงินจริงแล้วแต่ขึ้น Trial หมด ให้ผู้ดูแลตรวจ Subscription กับข้อมูลชำระเงินจริงก่อน ไม่ควรใช้การต่อ Trial แทนการแก้ข้อมูลแพ็กเกจ

## ทดสอบและข้อจำกัด
- npm run check ผ่าน (syntax เท่านั้น)
- Node / SQLite ในเครื่อง 98 เคสผ่าน ไม่มีข้ามเคส: 42 enrollment + 30 leave + 26 HR daily summary
- Chromium 11 browser checks ผ่าน: หน้าสมัครจริงโหลดในหน่วยความจำ + component ผู้ดูแลจากโค้ดจริง ด้วย API responses สมมติ
- ไม่ใช่การทดสอบใน LINE/iOS จริง ไม่ได้ Deploy และไม่เชื่อม D1 จริง ไม่ส่ง LINE ไม่รับชำระเงิน
- ทดสอบ rollback เมื่อ audit หรือ UPDATE ล้มเหลว และกรณีสถานะเปลี่ยนพร้อมกัน
- ตรวจ duplicate การต่อวันเดิม: ไม่ต่อซ้ำ ไม่เพิ่ม audit ซ้ำ
- ตัวนับ Seat และ invite-use ของระบบเดิมไม่ได้ถูกออกแบบใหม่ในแพตช์นี้ จึงไม่อ้างว่าแก้ race condition สมัครพร้อมกันทั้งหมดแล้ว

รันทดสอบจากโฟลเดอร์โปรเจกต์ที่มี migrations เดิมครบ:
```
node --test scripts/test-enrollment-p931.mjs scripts/test-leave-regression-p931.mjs scripts/test-hr-daily-regression-p931.mjs
```
การทดสอบจำลองบั๊กเวอร์ชันเก่า 3 เคสต้องกำหนด P930_SOURCE, P929_SOURCE และ P927_SOURCE ไปยัง src/index.js ของเวอร์ชันนั้น มิฉะนั้นข้ามเฉพาะ reproduction case ผลที่แนบครั้งนี้กำหนดครบแล้ว

Browser test ต้องมี Python Playwright และ Chromium; ตั้ง executable_path ในไฟล์ทดสอบตามเครื่อง ไม่มีผลต่อ Worker ที่ Deploy

## ย้อนกลับ
คืนไฟล์ที่สำรองไว้และ Deploy อีกครั้ง ไม่มีตารางใหม่ต้องลบ
การย้อนโค้ดไม่ย้อนวันสิ้นสุด Trial ที่ผู้ดูแลยืนยันไปแล้ว หากจำเป็นต้องแก้วัน ให้ผู้ดูแลตรวจ audit_logs และแก้เฉพาะบริษัทนั้นตามกระบวนการของระบบ ห้ามแก้ Subscription ทุกบริษัทพร้อมกัน
